工程报告 · 2026-09-12

StudyBoard 学习看板

一个离线优先的桌面学习工具。这份报告讲四件事：它长什么样、用的什么方法、 踩过什么坑、以及我认为做得不合理、该改的地方——包括产品交互和我们协作的流程。

一、它是什么

课程表、笔记库、课程卡片、网站门户、资料库、AI 助手、Notion 同步，装在一个 约 110 MB 的安装包里。核心特征有三个：

特征含义
离线优先 不监听任何端口，不依赖网络。数据全在你本机，断网照常用。
笔记就是文件 笔记库目录就是一个 Obsidian Vault。你随时可以用别的编辑器改它，应用会自己跟上。
零框架 界面用原生 TypeScript + Web Components 写的，没有 React/Vue 那层。体积小、启动快、不会因为框架升级而失效。

四、方法：这个工程是怎么做的

4.1 一切能自动验证的，都固化成测试

11 个测试场景，每一个都真的启动应用、注入探针、操作界面，而不是「跑一遍看它没崩」。 这里有一条硬规矩：断言的是数据到位，不是元素存在。

举个例子——输入框是页面搭好就存在的，里面的值要等异步加载才填上。 如果测试看到输入框在就往下走，它会拿到一个空值然后报一堆假错。 所以测试里专门有「等到值等于某内容」这类等待函数。

更关键的是：状态变化要断言在磁盘上。「已学库里看得见这张卡片」只说明内存里是已学，重启就没了。所以卡片测试会直接去读 cards.json，确认字段真的写进去了。

4.2 安全：把攻击者写进测试

安全不是靠「我们考虑到了」，是靠固化成探针、每次改动都重跑。 威胁模型设成最坏情况：假设界面里已经住进了一段攻击者的内容—— 这很现实，因为这个应用本来就要渲染你导入的 Markdown。

两轮共约 15 组攻击手法，全部通过。第二轮补的是「不用脚本」的攻击面：

攻击面结果
间接拿系统权限（构造器链、iframe）全部挡住
用 base / form / object / meta 绕过安全策略全部未生效
地址伪装（空白、换行、协议相对、UNC 路径）全部拒绝
资源协议穿越（编码、NUL 截断、超长路径）全部 404
资料伪装（exe 改名叫 pdf）、批量超限全部挡住
没配密钥时偷发请求到 AI / Notion拦在发请求之前
从界面读回明文密钥不存在这种接口
真实缺陷 · 已修

用系统默认程序打开一个 cmd.exe 链接。 笔记里写一行指向本机程序的链接，Markdown 会原样渲染，用户一点，系统就执行了那个程序。根因是两处代码注册同一个监听器时，后注册的把带协议白名单的版本整个顶掉了——白名单静默失效。

修法：这类监听器只允许在一处注册。回归测试里加了「点这个链接必须被拒」的断言。

真实缺陷 · 已修

改个笔记名，笔记就「消失」了。 把标题改成 .. .. x 这类以点开头的内容后，文件写出来了、索引也更新了，但目录扫描会跳过点开头的文件，于是下一次对账判定「它被外部删除了」，就摘掉索引、解绑卡片——文件明明还在磁盘上，界面里凭空没了。

根因是「应用能写出来的文件名」和「应用能扫回来的文件名」不是同一组集合。修法是让清洗规则两侧对称。

五、经验与教训

5.1 最危险的测试失败：恒真的「假通过」

这一轮抓到的四个例子，全都是同一个病——断言在「没修好」的时候也照样为真。

  • 类型判断陷阱。 typeof null 的结果是 "object"。有段探针写出了「空值也会被当成拿到了权限」的写法，于是安全状态被报成了漏洞。
  • 用错工具测协议。 安全策略里只允许图片走自定义协议，不允许 fetch 走。探针却用 fetch 去测——结果连正常图片都读不到，它还以为自己验的是「有没有被拦住」。
  • 把「效果被阻止」当成「元素不存在」。 安全策略禁止 base 标签生效，但标签本身仍然能插进页面。用「页面里有没有这个标签」当判据，永远为真。
  • 把「没抛异常」当成「被拦住了」。 我们的接口在拒绝时是返回一个失败对象，而不是抛异常。探针写成 try { ...; 没报错就是拦住了 } catch {}，这个分支永远会走到——即使把整个门禁删掉也照样通过。
规矩

凡是「拦住了没有 / 拒绝了没有」的断言，写完先故意破坏一下被测的那道关卡，看断言会不会变红。不会红的断言比不写更糟，因为它给的是虚假的安全感。

5.2 单例监听器：后注册覆盖先注册

就是第四节那个高危缺陷的通用形态。「注册一个监听器」听起来是人畜无害的操作，但在 Electron 里，某些监听器是全窗口唯一的一个——后注册的把先注册的整个替换掉，而不是叠加。安全代码被业务代码悄悄顶掉，没有任何报错。

5.3 读写两侧的合法集合必须成对设计

就是那个「笔记消失」缺陷的通用形态。能写出来的东西，必须能被读回来——这句话听起来像废话，但实际代码里，「写入时清洗」和「扫描时过滤」经常写在两个不同的文件里，各自看着都对。

5.4 注释要写「为什么」，不是「做什么」

这个项目的注释密度很高，但几乎都在解释取舍和反直觉的地方。比如：

// 先落盘再收尾：移入回收站是 Windows 的 Shell 操作，
// 可能要等上几百毫秒甚至更久，放在 persist 前会让 IPC
// 迟迟不返回、界面卡在「导入中」。

「移入回收站」这个调用本身一看就懂。值钱的是为什么它必须排在落盘之后——这是踩过才知道的。

六、我认为交互逻辑不合理的地方

以下是读代码时觉得别扭、但当时没改的。按严重程度排。

6.1 资料删除没有二次确认 该改

资料卡片上的删除按钮，点下去直接就删了，没有任何确认。而笔记删除是有两道确认的。 更麻烦的是，资料进的是回收站——但这件事只写在悬停提示里，不悬停就看不到。

资料常常是从课程网站扒下来的，原处可能已经没有了。建议：要么加确认，要么在按钮旁边常驻一行「将移入回收站」的小字。

6.2 冲突解决像做 20 道判断题 建议改

Notion 同步的冲突处理是「逐条问你」——方向是对的，你也明确要求「每次都问」。 但一次最多报 20 条冲突，真出现的时候，你要点 20 次。

建议：保留「每次都问」，但加一个「剩下的都按本地为准 / 都按远端为准」的批量按钮。决定权还在你手上，只是不用重复 20 次同样的判断。

6.3 导入失败时，真正的原因会被淹掉 建议改

一次拖 31 个文件进去，你会看到 31 条错误：1 条「一次最多导入 30 个」， 外加 30 条「文件不存在」。后 30 条是噪音——它们只是因为前 30 个被跳过了。 真正该看的只有第一条。

建议：超批量时直接返回，不要继续逐个试；或者把「整体性失败」和「单文件失败」分开显示。

6.4 给不存在的资料改归属，界面毫无反应 建议改

如果某份资料因为外部改动已经没了，你再点「归属到某课程」， 界面会什么都不发生，也没有任何提示。你会以为是点歪了。

建议：至少弹一句「这份资料已经不在了」。

6.5 内部的指纹字段出现在你可见的笔记里 开放问题

同步用的笔记 ID 写进 frontmatter 是对的（跨系统绑定必须显式）。 但另有一个纯粹是应用内部簿记的指纹字段也写了进去——你用 Obsidian 打开会看到它， 而它对你毫无意义，还让文件头变长。

之所以没改：把它挪进应用索引的话，换机器或重建索引后会全量重推一次同步。 这个取舍我没想清楚，所以维持了现状。列为开放问题。

6.6 选了「再等一会儿」之后就没有下文 小问题

界面卡住时会弹一个对话框，两个选项：「重新载入界面」和「再等一会儿」。 选后者之后，如果界面一直不恢复，你不会再收到任何提示——只能自己想起来还有这么个对话框。

建议：等 N 秒仍然卡着的话，再弹一次，明确说「还是没有响应」。

七、协作流程上可以优化的地方

回看这个项目的记录，我发现几个流程层面的问题——它们跟代码质量无关，但确实让效率打了折扣。

7.1 「写完了」和「提交了」没有及时对齐

这一轮开始的时候，我重新验证发现：上一轮的资料库、AI、韧性那批代码 写完而且测试全过，但没有提交。工作停在了「代码写好了」，而不是「这一轮结束了」。

后果是我得先花时间摸清「哪些是完成未提交、哪些是真没做」，才能判断该怎么继续。

改进

每轮收尾的完成定义里应该包含提交。测试通过 ≠ 这一轮结束。

7.2 有脚本，但从来没跑过

项目里一直有「打 Windows 安装包 / 打 Mac 安装包」这几个命令，但打包工具 从来没有被装进依赖里。也就是说——这个仓库此前从没真正打过包。

而「必须有打包好的安装包」是项目最早定下的硬约束之一。它一直停留在纸面上， 没有人发现，直到这次真的去跑。

改进

硬约束要有对应的、真的跑过一次的证据。加脚本的同时跑一次，或者明确标注「未验证」。

7.3 「已知未做」是个平铺列表，没有优先级

项目记录里有一个「已知未做」清单，这是好习惯。但里面五件事平铺在一起： Linux 支持、工程报告、打包验证、同步的联网实测、一个偶发失败的测试。 它们的紧急程度完全不同，却长得一模一样。

改进

给每条加上「为什么没做」和「什么情况下必须做」，否则接手的人无法判断该先动哪个。

7.4 偶发失败的记录方式不够可操作

有个测试偶发失败过一次，当时的判断是「机器负载高时文件监听来不及触发」， 记录成了「没复现到稳定失败，未修」。

这个判断可能是对的，但记录方式让下一个人没法接续：没写清当时的负载情况、 失败时的具体输出、重跑了几次。它只会变成一条永远没人碰的脚注。

改进

偶发失败要留下可复现的配方——并发场景、机器状态、具体输出。

7.5 测试代码被打进了安装包

那 1000 多行测试代码（包含所有攻击探针和攻击载荷字符串）被打进了生产安装包， 只靠一个环境变量控制开关。正常使用不会触发，任何人都能设那个变量把它拉起来。

实际风险很低——里面的攻击载荷都是 evil.example.com 这类占位地址， 没有杀伤力。但它本不该出现在你下载的东西里。

7.6 我自己的一次疏忽

这一轮我改了资源协议的路径处理代码，当时只跑了安全测试，是后来才补跑全套确认没有连带影响。 路径处理是被多个模块间接依赖的公共代码，改它理应立刻跑全套。

改进

改动公共代码后立即跑全套测试，不要等「顺便」再跑。

九、回答你最关心的几个问题

安全吗

是。约 15 组攻击手法全部通过，而且不是只测开发版——打包出来的安装包实跑了一遍完整探针，退出码 0。没有监听端口，开发者工具在生产包里确实关着，源码没有泄漏。

别人下载后会崩吗

不会。实测正常启动、建数据目录、无报错。而且即使真出问题也有分层兜底：首屏加载失败会提示「可能安装包不完整，建议重新下载」；界面进程崩了会自动重载（限 3 次，防止死循环）；反复崩就停下来告诉你日志文件在哪。

程序卡死有救吗

界面卡死：有救。 卡住超过阈值会弹对话框，让你选择「重新载入界面」。笔记有自动保存，最多丢最近一次自动保存之后敲的字。已实测确认这条通道确实挂在窗口上。

主进程自己卡死：没有真正的好办法。 连对话框都弹不出来，只能靠任务管理器强杀。这是 Electron 这类架构的固有限制，项目里如实写明了，没有假装能解决——能缓解的只是「主进程不干重活」这条纪律：所有可能耗时的活儿（图片解码、PDF 排版、网络请求）都不在主进程的启动路径上。

数据安全吗

所有内容都是原子写入的——写入过程中断电或被强杀，只会留下一个临时文件，不会损坏已有数据。删除的笔记进回收站而不是真删。密钥用系统钥匙串加密，界面读不回明文。
