## 一、项目一句话

**离线优先的学习看板桌面应用**：课程表、笔记库（就是 Obsidian Vault）、
课程卡片三态、网站门户、课程资料库、AI 助手、Notion 同步。
Electron 44 + 原生 TypeScript + Web Components，**零前端框架**。

仓库 `D:\ambigulous_ideas\study-board`，版本 0.1.0。

## 二、工程结构

### 2.1 进程分层

```
src/
├── shared/      11 个文件   契约层：类型、通道名、API 签名、纯逻辑（markdown / notion / limits）
├── main/        39 个文件   能力层：唯一持有系统权限的地方
│   ├── services/  22 个     各功能域的实现（notes / cards / materials / notion / ai / secrets…）
│   ├── ipc/       16 个     每个域一个文件，只做「校验入参 → 调 service」
│   ├── security.ts          安全基线（窗口守卫、协议、权限）
│   ├── resilience.ts        崩溃与卡死的自救
│   ├── smoke.ts             冒烟测试harness（1000+ 行，只在 STUDY_BOARD_SMOKE=1 时启用）
│   └── paths.ts             所有路径的唯一出处
├── preload/     1 个文件   安全边界：contextBridge 暴露固定方法集
└── renderer/    34 个文件   界面层
    ├── components/  12 个   可复用组件（表单、网格、面板）
    ├── views/        9 个   页面级视图
    └── lib/         13 个   工具（ipc 包装、主题、编辑器、性能）
```

约 19000 行 TypeScript。主进程 + preload 输出 **CJS**。

### 2.2 三条贯穿全项目的约定

1. **通道四处齐步**：新增 IPC 必须同时在 `shared/channels.ts`（白名单）、
   `shared/api.ts`（签名）、`main/ipc/*`（实现）、`preload/index.ts`（暴露）出现。
   漏了会在启动时被 `assertAllChannelsRegistered()` 立刻抓住。
2. **路径只从 `paths.ts` 出**，且一律过 `safeJoin`。渲染层从不传完整路径，
   只传 id 或收件箱内的文件名。
3. **依赖放哪由构建配置决定**：主进程/preload 有 `externalizeDepsPlugin` →
   放 `dependencies`；渲染层没有、全打进 bundle → 放 `devDependencies`。
   放错的话 electron-builder 会把同一份代码再打一份进安装包。

### 2.3 数据设计

**不用数据库**。结构化数据是原子写入的 JSON（tmp + `renameSync`），
笔记本体是磁盘上的 `.md`。

| 存什么 | 放哪 | 为什么 |
| --- | --- | --- |
| 笔记 | 用户可选的库目录（Obsidian Vault） | **磁盘上的 .md 才是本体**，索引只是缓存 |
| 课表 | `timetable.json` | 形状与内容分离 |
| 卡片 | `cards.json` | 三态只是 status 字段，不是第二份存储 |
| 资料 | 笔记库内 `attachments/` | 跟笔记待在一起，Obsidian 原生能预览 |
| 密钥 | `secrets.bin`（safeStorage 加密） | 只有密文，明文永不落盘 |

放弃 SQLite 的理由：`sql.js` 按路径找 wasm，asar 后最容易崩；
`node:sqlite` 会把数据锁进二进制、人读不了、外部编辑器也改不了——
而「用户能用 Obsidian 直接改」是这个项目的核心卖点之一。

## 四、方法：这个工程是怎么做出来的

### 4.1 一切能自动化验证的，都固化成冒烟场景

**11 个场景**（`npm run smoke:<name>`），每个都真跑 Electron 窗口 + 注入探针：

```
basic / timetable / portal / cards / notes / sync / export / ai / notion / security / materials
```

这不是「跑一遍确认没崩」，而是**断言语义状态**：

- 等的是**数据到位**，不是元素存在。输入框是页面搭好就存在的，值要等异步加载才填上
  ——所以有 `waitForValue` / `waitForText` / `waitForTextChange`，而不是
  `querySelector` 拿到就往下走。
- **状态变化要断言在磁盘上**。「已学库里看得见这张卡片」只证明主进程**内存**里是
  `learned`，重启就没了。所以 `:cards` 直接去读 `cards.json`。

### 4.2 性能基准：判定差异的硬标准是区间不重叠

`npm run bench` 真跑 Electron 窗口写 JSON；`bench:compare` 比两次结果。
**测量纪律**：等语义信号再开计时。判定差异的唯一硬标准是
**两组区间不能重叠**——重叠就老实写「无差异」，不挑好看的样本。

对比旧代码用 `git worktree` + node_modules Junction 链接，跑完清理干净。

### 4.3 安全：把攻击者写进测试

安全不是靠「我们考虑到了」，是靠**固化成探针、每次改动重跑**。
威胁模型是「渲染层里已经住进一段攻击者的内容」——这很现实，
因为应用本来就要渲染用户自己或从别处导入的 Markdown。

详见 `SECURITY.md`，两轮共 9+6 组手法，记录在案。

### 4.4 文档分工

| 文件 | 回答什么 |
| --- | --- |
| `ARCHITECTURE.md`（1073 行） | **为什么这么做**。代码里能看出来的不重复 |

| `PERFORMANCE.md` | 基准方法与历史数据 |
| 本文件 | 工程怎么被做出来的，包括做错的 |

### 4.5 记忆与技能

## 五、经验与教训

### 5.1 写测试最危险的失败模式：恒真的假通过

**本轮抓到的三个例子，全都是「断言在没修好时也照样为真」：**

1. **`typeof null === 'object'`。** 探针写
   `typeof (window.opener && window.opener.process)`。`opener` 为 `null`（**正是期望的
   安全状态**）时表达式得到 `null`，`typeof` 返回 `'object'`——安全被报成逃逸。
2. **用 `fetch` 读自定义协议。** CSP 的 `connect-src 'self'` 不含 `sb-asset:`，
   所以 `fetch` 一律 `Failed to fetch`。探针退化成「什么都测不出来」——
   连正常图片都读不到，而它还以为自己在测「有没有被拦住」。
3. **把「效果被阻止」当成「元素不存在」。** CSP 的 `base-uri 'none'` 挡的是效果，
   `<base>` 照样能进 DOM。用 `querySelector('base') !== null` 判断，永远为真。

上一轮还有一个更隐蔽的：**preload 的 `invoke()` 是返回 `{ok:false, error}`
而不是抛异常**。写成 `try { await ...; /* 没报错 = 拦住了 */ } catch {}`，
这个分支**永远会走到**——即使把整个门禁删掉也照样通过。

> **规矩**：凡是「拦住了没有 / 拒绝了没有」的断言，写完先**故意破坏一下被测的守卫**，
> 看断言会不会变红。不会红的断言比不测更糟，因为它给的是虚假的安全感。

### 5.2 单例注册 API：后注册覆盖先注册

`setWindowOpenHandler` 是「后来居上」的。`security.ts` 里注册了带协议白名单的
安全版，`window.ts` 里又注册了一个直接调 `shell.openExternal(url)` 的裸版本——
后者把前者**整个顶掉**，协议白名单静默失效。

攻击链很直接：笔记里写 `<a href="file:///C:/Windows/System32/cmd.exe" target="_blank">`，
Markdown 按 `html: true` 原样渲染，用户一点 → 系统执行 cmd.exe。

> **规矩**：这类单例 handler 只在 `security.ts` 注册一次，别处不许再注册。

### 5.3 「能写出的」必须等于「能扫回的」

`safeNoteTitle` 只洗路径分隔符，放行 `.` 开头的标题；而目录扫描为了跳过
`.study-board`/`.obsidian` 会忽略 `.` 开头的文件。两组集合不一致的后果：
重命名笔记为 `.. .. x` → 文件写出来、索引更新 → 下次对账扫不到它 →
判定「被外部删除」→ **摘索引、解绑卡片、落盘**。文件还在磁盘上，界面里凭空消失。

> **规矩**：读写两侧的合法集合必须成对设计。

### 5.4 文件监听的三个坑

1. **自写标记用指纹不用时间窗**。写完立刻 stat 记 `size + mtimeMs`，收到事件再比。
   时间窗短了漏、长了会吃掉用户紧接着的外部修改。不过滤的后果是
   **每打一个字编辑器就被重载一次**。
2. **不信事件类型**。一批事件防抖合成集合后重扫目录，配 `awaitWriteFinish` 挡半截文件。
3. **删除要两次确认**（隔 800ms），挡「先删原文件再写新的」式保存。
   且确认趟要**直接看文件在不在**，不能再看对账结果——第一次对账已经把索引删了，
   第二次不再报，于是永远等不到确认，删除反而整个丢了。

### 5.5 修改前先清 dirty 标记

正在编辑的笔记被外部改动时，弹确认让用户选。选「载入磁盘版本」前
**必须先清 `dirty`**——否则 `open()` 开头的 `flush()` 会把用户刚决定丢掉的内容写回去。

### 5.6 中文注释要写「为什么」，不是「做什么」

这个仓库的注释密度很高，但几乎都在解释**取舍与反直觉的地方**：

```ts
// 先落盘再收尾：移入回收站是 Windows 的 Shell 操作，可能要等上几百毫秒甚至更久，
// 放在 persist 前会让 IPC 迟迟不返回、界面卡在「导入中」。
```

「移入回收站」这个调用本身一看就懂，值钱的是**为什么它必须排在 persist 之后**——
这是踩过才知道的。

## 六、我认为用户交互逻辑不合理的地方

以下都是我在写代码/读代码时觉得**别扭**、但当时没改的。按我判断的严重程度排。

### 6.1 严重：资料删除没有二次确认

`materials-grid.ts` 的删除按钮 `title="删除（进回收站）"`，点下去直接调用，
**没有任何确认对话框**。而笔记删除是有两道确认的（隔 800ms）。

不一致且危险：资料是用户从课程网站扒下来、可能已经不在原处了的文件。
虽然进的是回收站，但**用户不知道**——按钮文案藏在 tooltip 里，而 tooltip 要悬停才出现。

> 建议：要么加确认，要么在按钮旁边常驻一个「将移入回收站」的小字说明。

### 6.2 中等：冲突解决要逐条点，20 条就是 20 次

Notion 拉取的冲突处理是「先问我，每次都问」——这是用户明确选的，交互方向对。
但 `MAX_NOTION_CONFLICTS = 20`，真出现 20 条冲突时，用户要点 20 次。

> 建议：保留「每次都问」的前提下，加一个「剩下的都按本地为准 / 都按远端为准」的
> **批量按钮**——仍然由用户决定，只是不必重复 20 次同样的判断。

### 6.3 中等：导入失败的反馈分层不清楚

资料导入的契约是「逐条独立成败，失败原因回传」`{added, errors}`。
31 个文件超批量时，`errors` 里会有**1 条「一次最多导入 30 个」+ 30 条
「ENOENT: no such file or directory」**。

后 30 条是噪音——用户真正需要知道的只有第一条。现在它们平铺在一起，
真正的那个原因会被淹掉。

> 建议：超批量时**直接返回**，不要继续逐个尝试那 30 个；或者把
> 「整体性失败」与「单个文件失败」分成两组显示。

### 6.4 中等：`setCard` 传不存在的 id 静默成功

`materials.setCard({ id: 'x', courseCardId: 'no-such' })` 返回 `ok:true` + 空列表。
资料不存在时 `return this.list()`——**不报错**。

界面上的后果：如果因为某种原因（外部改动、索引不同步）资料已经没了，
用户点「归属到某课程」会看到界面毫无反应，没有任何错误提示。

> 建议：资料不存在时至少给一个「这份资料已经不在了」的提示。

### 6.5 轻微：`notionHash` 这个内部字段会出现在用户的 frontmatter 里

把 `notionId` 写进 frontmatter 是对的（外部系统 ↔ 本地笔记的绑定必须显式）。
但 `notionHash` 纯粹是**应用的簿记**——它出现在用户用 Obsidian 打开文件时看到的
YAML 里，而它对用户毫无意义，还会让 frontmatter 变长。

> 建议：指纹可以不落 frontmatter（记在应用的索引里即可）。
> 但代价是换机器/重建索引后会全量重推一次——**这个取舍我没想清楚**，
> 所以当时维持了现状。留作开放问题。

### 6.6 轻微：「再等一会儿」之后没有下文

卡死对话框有两个按钮：「重新载入界面」/「再等一会儿」。选后者之后，
如果界面**一直**不恢复，用户不会再收到任何提示——他只能自己想起来还有这么个对话框。

> 建议：用户选「再等一会儿」后，如果 N 秒内仍然 unresponsive，再弹一次
> （说明「还是没有响应」）。现在是一次性的。

## 七、从对话与记忆数据里看，协作方式可以优化的地方

以下是回看这个项目的记忆文件、技能与对话过程，我发现的**流程层面**的问题。

### 7.1 「已完成」与「已提交」没有及时对齐

这一轮开始时，我重新验证发现：上一轮的资料库/AI/韧性代码**写完且全部测试通过**，
但**没有提交**——工作停在「代码写好了」，而不是「这一轮结束了」。

后果是我必须先花时间摸清「哪些是已完成未提交、哪些是真没做」，
再回头问用户范围。

> 改进：**每轮收尾的完成定义里必须包含提交**。测试通过 ≠ 这一轮结束。

### 7.2 有脚本却从来没跑过

`package.json` 里 `package:win` / `package:mac` / `package:all` / `package:dir`
四个脚本一直在，但 **`electron-builder` 从来没被装进 devDependencies**。
也就是说这个仓库**此前从未真正打过包**——「必须有打包好的安装包」是硬约束之一，
而它一直是纸面上的。

同类问题：如果某个东西没进过 CI，就不能假设它可用。

> 改进：**硬约束要有对应的、真的跑过一次的证据**。加脚本的同时跑一次，
> 或者在 README 里明确标注「未验证」。

### 7.3 记忆里堆着「已知未做」，但没有优先级

`MEMORY.md` 末尾有「已知未做」清单，这是好习惯。但它是个平铺列表：
Linux 支持、工程报告、打包验证、Notion 真实联网验证、sync 时序抖动——
五件事的紧急程度完全不同，却长得一样。

> 改进：给每条加上「为什么没做」与「什么情况下必须做」，
> 否则下次接手时无法判断该先动哪个。

### 7.4 偶发失败的记录方式不够可操作

`sync` 场景有一次偶发失败，判断是「负载下文件监听来不及触发的时序抖动」，
记录为「未复现到稳定失败，未修」。

这个判断可能是对的，但**记录方式让下一个人无法接续**：没写清当时的
负载条件、失败时 renderer 自检的具体值、重跑了几次。

> 改进：偶发失败要留下**可复现的配方**（并发场景数、机器负载、观察到的具体输出），
> 否则它只会变成一条永远没人碰的脚注。

### 7.5 测试脚本与产品代码没有隔离

`smoke.ts`（1000+ 行，含全部攻击探针与 payload）被**打进了生产包**，
只靠 `STUDY_BOARD_SMOKE=1` 环境变量门控。

这是「把测试放在 src/ 里、由同一套构建管线处理」的直接后果。

> 改进：构建期用条件编译或别名把 smoke 排除出生产产物。

### 7.6 我自己的一个流程问题：改完没立刻重跑全套

这一轮我改了 `assetProtocol.ts`（`pickHash` 的大小写处理），
当时只跑了 `smoke:security`，是**后来**才补跑全套 10 个场景确认没回归的。

路径处理是被多个场景间接依赖的公共代码，改它理应立刻跑全套。

> 改进：**改动公共代码后立即跑全套**，不要等「顺便」再跑。

## 九、给接手者的话

1. **先读 `MEMORY.md`**，那里是密度最高的信息。
2. **加新模块按 `study-board-module` 技能的 13 步清单做**，踩坑清单能省你很多时间。
3. **改公共代码后立刻跑全套冒烟**（见 7.6）。
4. **写断言先破坏被测的守卫**，确认它会变红（见 5.1）。
5. 这个项目最值钱的东西不是代码，是 `ARCHITECTURE.md` 里那些**为什么**——
   它们大多是用一次返工换来的。
