# 架构说明

这份文档记录**为什么这么做**，而不是做了什么 —— 代码里能看出来的东西这里不重复。

---

## 一、硬约束

项目的所有技术选型都服从四条约束，它们来自最初的产品讨论：

1. **不依赖用户电脑上会自己升级的东西**（系统浏览器、WebView、系统组件）
2. **运行时依赖越少越好，最好自带**
3. **版本变动不能导致功能失效**
4. **Windows 和 macOS 表现一致，一套代码**

这四条反过来决定了形态选择的方向：**自带运行时 > 借用系统运行时**。

---

## 二、为什么是 Electron

| 候选 | 判定 | 原因 |
| --- | --- | --- |
| **Electron** | ✅ 采用 | 自带 Chromium，渲染层与系统版本完全解耦；`electron-builder` 是全平台安装包最成熟的方案；不需要开端口 |
| Tauri v2 | ❌ 放弃 | 体积优势明显，但依赖系统 WebView —— Windows 用 WebView2、macOS 用 WKWebView，而 WebView 会随系统更新变化。这正好撞在第 1、3 条约束上 |
| 本地 HTTP 服务 + 浏览器 | ❌ 放弃 | 依赖用户浏览器（差异最大），需要开本地端口（与「不暴露端口」的诉求相冲），还可能被防火墙弹窗拦截 |

**代价**：安装包 80–150 MB，以及 macOS 未签名时的 Gatekeeper 提示。

**跨平台构建的边界**：一个代码库能同时支持两套系统，但**构建**必须在各自系统上进行。仓库里用 GitHub Actions 解决：推 tag 后 Windows runner 出 `.exe`，macOS runner 出 `.dmg`。

---

## 三、技术栈

| 层 | 选型 | 为什么是它 |
| --- | --- | --- |
| 外壳 | Electron | 见上 |
| 主进程 | Node + TypeScript | 唯一持有系统权限的地方 |
| 界面层 | 原生 TypeScript + Web Components | 零框架。没有框架版本周期，产物体积最小，性能最好 |
| 构建 | electron-vite + Vite | 主进程/preload/渲染层三段式构建，开发时热更新 |
| Markdown 编辑 | CodeMirror 6 | 纯 JS、无框架绑定、社区成熟 |
| 富文本编辑 | TipTap（ProseMirror） | 功能集最接近 Word，扩展机制清晰 |
| md ↔ HTML | markdown-it + turndown | 两个都是纯 JS，无原生依赖 |
| Word 导出 | docx | 纯 JS 生成 `.docx`，不需要本机装 Office |
| PDF 导出 | Electron `printToPDF` | 内置能力，零额外依赖，最不容易坏 |
| 结构化数据 | 原子写入的 JSON 文件 | 零依赖、零原生编译、人能直接读；数据量本就很小，详见第五节 |
| 文件监听 | chokidar | 跨平台行为比 `fs.watch` 一致得多 |
| HEIF 解码 | libheif-js | 纯 JS/WASM，**不调系统图像库** |
| 打包 | electron-builder | Windows NSIS + macOS dmg |

### 关于「不调系统库」

HEIF 解码是最典型的一个例子。macOS 有原生 HEIF 支持，Windows 需要额外的编解码器包，如果调用系统能力，就会出现「同一份代码在两个系统上表现不同，甚至随系统更新失效」。

所以这里选了 `libheif-js`：用纯 JS/WASM 解码，慢一点，但**行为在任何系统、任何版本上都完全一致**。这个取舍在项目里是通用原则 —— 凡是能用纯 JS 解决的，就不调系统能力。

## 四、进程架构

```
┌─────────────────────────────────────────────┐
│ 渲染进程（界面层）                            │
│  · 课表 / 门户 / 卡片 / 编辑器                │
│  · sandbox: true, nodeIntegration: false     │
│  · CSP: default-src 'none'                   │
└──────────────────┬──────────────────────────┘
                   │ 只有白名单方法
┌──────────────────▼──────────────────────────┐
│ preload（安全边界）                           │
│  · contextBridge 暴露固定方法集               │
│  · 通道名写死，渲染层无法拼接                  │
└──────────────────┬──────────────────────────┘
                   │ IPC
┌──────────────────▼──────────────────────────┐
│ 主进程（能力层）                              │
│  文件读写与监听 · JSON 存储 · HEIF 解码        │
│  AI / Notion 代理 · 密钥加密                  │
└─────────────────────────────────────────────┘
```

**没有 HTTP 服务，没有端口。** 这是刻意的：本地 HTTP 意味着要处理端口占用、防火墙规则、以及「万一绑到了 0.0.0.0 怎么办」。走 IPC 这些问题全部不存在。

### IPC 的三个约定

写在 `src/main/ipc/index.ts` 里，所有处理器都必须遵守：

1. **通道必须在 `src/shared/channels.ts` 白名单里** —— 随手新增通道会在启动时直接报错
2. **调用方来源必须可信** —— 只接受来自本应用页面的调用
3. **异常必须收敛成 `IpcResult`** —— 渲染层永远拿不到主进程堆栈

另外还加了启动自检 `assertAllChannelsRegistered()`：声明了却没实现的通道会立刻暴露，未实现的功能由 `ipc/pending.ts` 统一挂占位，返回可读的「开发中」提示，而不是底层报错。

## 五、数据设计

### 全部用 JSON 文件 + Markdown 文件（不用 SQLite）

最初选的是「SQLite（`sql.js`）+ Markdown」，实际落地时改掉了，理由很硬：

| 方案 | 问题 |
| --- | --- |
| `sql.js` | 运行时要用 `locateFile()` 去**磁盘上按路径找** `sql-wasm.wasm`。打包成 asar 之后这个路径解析是最容易出问题的一环，而且出问题时只在**用户机器上**才暴露 |
| `node:sqlite` | Electron 44 内置 Node 24.20，这个模块确实存在（但是 experimental）。它把数据锁在一个只能由本应用打开的二进制文件里 |
| **JSON 文件** | 零依赖、零原生编译、零 wasm 路径问题；数据人能直接读懂、能丢进 Git、出问题能手改 |

这个项目的数据量本来就小（门户站点十条量级、课程卡片几条到几十条、课表几十个单元格），
SQLite 的性能优势完全用不上，却要付出上面那些风险。而需求里反复强调的是
**「最底层、最通用的结构」「不要因为版本更新出兼容问题」**——JSON 文件在这两条上都是最优解。

顺带一个收益：`.md` 与 `.json` 都是人可读的纯文本，用户的数据**永远不会被锁死在本应用里**。

### 具体落盘

```
<数据目录>/
├── config.json          # 应用设置（主题、节数、AI / Notion 配置…）
├── secrets.bin          # API Key / Token，走系统钥匙串加密，不在这份文件里明文
├── timetable.json       # 课表内容：每节时间、单元格、图片索引
├── timetable_images/    # 课表照片本体
├── portal.json          # 网站门户站点
├── cards.json           # 课程卡片
├── icons_cache/         # 抓取到的站点图标
└── notes_library/       # 笔记库，直接就是 Obsidian Vault
```

所有写入都是**原子**的：先写 `xxx.json.tmp`，再 `rename` 覆盖。断电或崩溃也不会留下半个文件。
读取时如果 JSON 损坏，会把它改名成 `.broken` 留个现场，然后用默认值继续启动——**绝不因为一份文件坏了就起不来**。

### notes_library 的目录结构

```
notes_library/
├── 高等数学_张启明.md
├── 大学英语_Li Na.md
└── .study-board/
    ├── index.json      # id ↔ 文件名 映射
    └── trash/          # 删掉的笔记挪到这里，不真删
```

- 每篇笔记用 YAML frontmatter 存元数据（id、模式、时间），正文是纯 Markdown
- `.study-board/index.json` 是本应用自己用的索引，Obsidian 会忽略它
- 整个目录可以**直接作为 Obsidian Vault 打开**，不需要任何转换

**磁盘上的 .md 文件才是本体，索引只是加速用的。** 这条是整个笔记模块的地基：

- 用户在 Obsidian 里新增一个 `.md`，本应用下次 `list()` 就会认出来；
- 用户在 Obsidian 里改名 / 删除，索引跟着对账，不会留下幽灵条目；
- 索引文件丢了也能重建——新认领一个文件时，**优先沿用文件 frontmatter 里的 id**，
  所以课程卡片与笔记的关联不会因为丢一个索引文件就全断掉。

frontmatter 的解析与生成是自己写的（`services/frontmatter.ts`，约 100 行），
刻意没引 `js-yaml`：只需要「键值对 + 小数组」这一点子集，完整 YAML 规范
（锚点、多行折叠、类型标签）在这里全是永远用不到的攻击面。

一个细节：**时间戳写出去时强制加引号**。不加的话严格 YAML 解析器会把它读成
日期对象，于是同一份文件在不同工具里读出来一个是字符串一个是日期。
我们只要字符串——可预测比「聪明」重要。

### 双向同步怎么不打架

```
外部编辑器改文件 ──▶ chokidar 监听 ──▶ 去抖 ──▶ 更新界面（不写回文件）
界面里改内容     ──▶ 写文件         ──▶ 记录本次写入 ──▶ 监听器跳过自己写的那次
```

关键在于**写入要打标记**：主进程每次写文件前记下路径与内容哈希，监听器收到变更事件时先比对，是自己刚写的就跳过。否则会出现「改一次触发一次写回，写回又触发一次监听」的回环。

## 六、课程表模型

一个容易踩坑的点：**两种录入方式的数据必须同时保存**。`mode` 是**视图开关**而不是数据归属——用户在两种模式之间来回切，表格里填过的字和上传过的图都还在。这个设计直接来自需求里「两种方式互为补充」这句。

### 形状与内容分开放

```
config.json      →  mode / periodCount / weekdays        （形状）
timetable.json   →  rows / cells / images                （内容）
timetable_images/→  课表照片本体
```

分开的好处：调整节数不会碰内容，改内容也不会覆盖形状。两边各有自己的写入路径和校验规则，不会出现「保存单元格的时候顺手把节数写回默认值」这种事故。

节数从 11 改成 15 时，超出的行不删除、只是不展示；改回来内容还在。同理，`timetable.json` 里保存的「每节时间」也按节次索引存放，`buildRows()` 负责按当前节数补全成完整列表。

### 单元格

```ts
interface TimetableCell {
  courseName: string   // 课程名称
  teacher: string      // 授课老师
  location: string     // 授课位置
  duration: string     // 持续时间，自由文本："45 分钟" / "1-2 节连上"
  remark: string       // 备注
}
// key = "节次:列号"，列号 0 = 周一
```

`duration` 刻意做成自由文本而不是数值：现实里既有「45 分钟」这种单节，也有「1-2 节连上」这种跨节，用一个字符串兜住最省事。全空的单元格不落盘，等价于清空。

### 照片导入链路

Chromium 出于专利原因**不支持 HEIC/HEIF**，而苹果手机拍课表默认就是 HEIC，所以必须自己兜：

```
文件 → 是不是 HEIF？
        ├─ 是 → libheif-js（WASM 内联在 JS 里）解码 → RGBA → 纯 JS PNG 编码
        └─ 否 → 原字节
     → Electron nativeImage 解码（Chromium 负责，质量和性能都好）
     → 长边超过 2400px 就等比缩小（手机直出 4000px，课表只要看得清字）
     → PNG 源保持 PNG（截图转 JPEG 会糊字），照片类转 JPEG q88
     → 落盘 + 建索引
```

几个刻意的选择：

- **WASM 用 `wasm-bundle` 变体**：WASM 以 base64 内联在 JS 里，运行时不需要再去磁盘找 `.wasm` 文件——打包成 asar 之后照样能跑，也不会因为系统升级失效。代价是约 2MB，且**懒加载**（`require` 放在函数里），不用 HEIF 的人不付这份启动成本。
- **PNG 编码器自己写**（`src/main/services/png.ts`）：`nativeImage.createFromBitmap` 的字节序按平台而异，不可靠；先转成 PNG 再交给 `nativeImage` 是最可预测的路子。只用 Node 内置 zlib，零依赖。
- **失败要降级而不是报死**：如果 `nativeImage` 读不了某个格式，就原样保留原始字节；只有 HEIF 解码失败才真的拒绝（因为渲染不出来）。
- **单张失败不影响其它**：逐张处理，失败原因带着原文件名回传给界面，用户知道哪张为什么没进来。

### 交互

- **悬停预览**：鼠标停 170ms 后浮出信息卡，显示该格的完整内容；编辑弹层打开时不弹，避免两层浮层叠在一起。
- **双击编辑**：就地弹表单，`Ctrl/⌘ + Enter` 保存、`Esc` 取消、单行输入里回车即存。
- **键盘可达**：单元格 `tabindex=0` 且 `role=button`，回车 / 空格同样能打开编辑。
- 浮层全部是 `position: fixed` + `div` 手写实现，不用原生 `<dialog>` 或 Popover API——后者在较早的 Chromium 上行为有差异，与「不依赖会随系统升级而变的东西」这条硬约束冲突。

## 七、笔记的双模式互转

需求要的是「md 或 Word 二选一，且要有二者主要功能」，最终选择了**双模式可切换**。

实现上，**只有一份 `.md` 源文件**：

```
        ┌──────────────┐
        │  x.md 源文件  │
        └──┬────────┬──┘
   读取    │        │   读取
   ┌───────▼──┐  ┌──▼────────┐
   │Markdown  │  │ 富文本视图 │
   │ 编辑器   │  │ (TipTap)  │
   └───────┬──┘  └──┬────────┘
           │        │
   markdown-it     turndown
           └───►◄───┘
```

**已知代价**：Markdown 表达不了的能力（合并单元格、字体颜色、字号）在互转时会退化。处理方式是**切换前弹窗提示并自动备份**，而不是假装没有损失。

之所以没选「md 和 html 各存一份」，是因为两份数据一旦不一致，用户根本无从判断哪份是对的。

## 八、兼容性策略

针对「怕版本更新导致失效」这个诉求，具体做了这些：

| 措施 | 作用 |
| --- | --- |
| `.nvmrc` + `package-lock.json` | 构建环境完全可复现 |
| CI 固定 Node 版本 | 本地和 CI 行为一致 |
| 不使用原生模块（`.node`） | 不需要 `electron-rebuild`，也不会有 ABI 不匹配 |
| HEIF 等能力用纯 JS | 不因系统组件升级而失效 |
| 渲染层不用新语法 | 只有 Chromium 版本会变，而它是随包固定的 |
| CSP 里区分开发/生产 | 避免「开发能跑、打包被拦」这类只在发布时暴露的问题 |
| `modulePreload: false` + 去掉 `crossorigin` | `file://` 场景下这两个属性会引发无意义的 CORS 校验 |

主进程输出的模块格式也刻意选了 **CommonJS** 而不是 ESM —— 兼容面更宽，不受 Electron 各版本 ESM 支持差异影响。

## 九、构建与发布

```
npm run dev       →  electron-vite dev，渲染层热更新
npm run build     →  三段式构建到 out/
npm run package:* →  electron-builder 出安装包到 release/<版本>/
```

```
out/
├── main/index.js        # CJS
├── preload/index.js     # CJS
└── renderer/
    ├── index.html       # CSP 已按环境注入
    └── assets/
```

`index.html` 里的 CSP 是构建时通过 `%CSP%` 占位符替换的，开发和生产的策略不同，用的却是同一份页面源文件。

## 十、性能与内存的取舍

完整的测量方法、实测数据、以及「试过但决定不做」的清单在
[docs/PERFORMANCE.md](./PERFORMANCE.md)。这里只记几条会影响以后改代码的原则。

### 测量纪律

- **量端到端，不量单点。** 用户感受到的是「双击 → 输入 → 保存 → 看到新值」整条链路，
  中间夹着 IPC 往返和落盘。分开量每个环节都很快，合起来才是真数字。
- **内存看进程工作集，不看 JS 堆。** 图片解码后的位图不在 JS 堆里记账，
  只看 `usedJSHeapSize` 会严重低估。
- **等「语义完成」的信号，不等 DOM 元素出现。** 导航按钮在 bootstrap 早期就存在，
  看它出现就点，量到的是两个页面互相争抢的结果。
- **预热轮次不计入统计。** 否则 p95 被 JIT 和首帧成本抬高，而且不可复现。
- **两组数据交替采。** 同一台机器不同时段的负载差异足以盖住要验证的优化。

### 会影响的代码约定

- **写方法返回 `void`，`get()` 是唯一深拷贝出口。** 不要再给写方法加返回值快照——
  调用方本来也不用，白白多一次 `structuredClone`。
- **保存单元格必须带 `RenderHint`。** 这是最高频的写操作，走单格重绘而不是整表重建。
  但结构变化（换模式 / 改节数 / 表头重命名）必须走整表重建，不要为了省事一律只画一格。
- **整表渲染与单格重绘共用同一份模板**（`cellInnerHtml()`）。
  两条路径各写一套模板，久了必然长得不一样，而且这类偏差很难被测试发现。
- **给 `<img>` 补 `width` / `height` 时，CSS 里必须同时有 `height: auto`。**
  否则 HTML 的 `height` 属性会当成长度提示生效，图片被拉成原始像素高。
- **`.sb-layer` 按需创建、空了摘掉。** 常驻一个全屏 `position: fixed` 容器会白占一层。
- **不要加没有测量支撑的 CSS 优化。** `contain` / `will-change` 这类属性能不加就不加，
  加了之后一旦出样式问题，很难定位到是它引起的。

### 已知的、刻意不做的

- **异步合并写盘**：能把文件写入移出关键路径，但进程异常退出会丢掉最后一次编辑。
  实测一次落盘 0.3~0.5ms，收益不值这个风险。
- **V8 编译缓存**：主进程产物仅 64 kB 且惰性编译，启动时间由 Chromium 决定（占 133ms），
  缓存对启动没有帮助；唯一受益者是懒加载的 libheif，而它本来就在关键路径之外。
- **IPC 返回增量而不是整份课表**：收益比已经落地的单格重绘小得多，
  代价是渲染层失去一份完整、唯一可信的状态快照。

## 十二、网站门户与「唯一会出网的地方」

### 需求

> 有一个集成界面便于快捷访问各个学习网站（默认的有慕课、B站、知网），
> 可以选择添加网站 —— 输入网址 → 给它命名 → 创建快捷方式和图标 → 点击即可直接访问

### 数据

`portal.json`，与课表同一套原子写入 + 损坏备份重建的规矩。内置站点用**固定 id**
（`builtin-mooc` / `builtin-bilibili` / `builtin-cnki`）而不是每次生成：
这样「已隐藏」的状态能一直对得上，不会一重启又冒出来。

内置站点**只能隐藏、不能删除**——需求里这三个是默认就该有的，删了用户找不回来。
界面上对应的删除按钮是 `disabled` 的，主进程也会再拒一次。

### 图标：默认不联网

这是整个应用里唯一会主动出网的功能，所以规则定得很死：

| 规则 | 原因 |
| --- | --- |
| **只在用户明确点击时触发**（「补齐图标」或单个站点的 ⟳） | 应用的默认状态必须完全离线，启动路径上不允许有网络 |
| 只走 `http` / `https`，重定向目标同样校验，最多 3 跳 | 防止被重定向到 `file:` 之类的协议 |
| `useSessionCookies: false` | 抓图标没有任何理由带上用户的登录态 |
| 网页正文 512 KB、图标 2 MB、单次 8 秒超时 | 体积与时长双重上限，避免一个坏站点拖住主进程 |
| 抓到后**一律交给 Chromium 解码再编码成 PNG（≤64px）** | 一举两得：既挡掉伪装成图片的 HTML / SVG，又把图标统一到固定尺寸 |
| 失败只影响图标 | 回退到「色块 + 首字」，站点本身照常可用 |

解析顺序是先读页面 HTML 找 `<link rel=icon>`（能拿到 180×180 的 apple-touch-icon，
比 `/favicon.ico` 清晰得多），找不到再退回站点根的 `/favicon.ico`。

图标字节**不走 IPC**，而是通过 `sb-asset://icon/<file>` 读取，与课表照片共用同一套
`assetProtocol` + CSP 放行机制。所以通道白名单里没有「读取图标」这一条——
本来就不需要。

### 界面

`components/portal-grid.ts` 是唯一的渲染器，概览页与管理页共用，区别只在 `editable`：

- 概览页（`editable: false`）：只显示未隐藏的站点，点一下直接开浏览器；
- 管理页（`editable: true`）：连隐藏的一起显示（半透明），带编辑 / 抓图标 / 隐藏 / 删除。

这和课表面板是同一个套路：**两处要展示同一份数据时，只写一个渲染器。**
各写一套迟早会出现「首页点了能开、管理页显示不出来」这类偏差。

打开链接走的是 `shell.openExternal`（经 `openExternalSafely` 校验协议），
不是让渲染层导航——渲染层的 `will-navigate` 本来就被拦死。

## 十三、课程卡片与笔记的联动

### 需求

> 以卡片形式展示课程（卡片可点击翻转）。卡片内容包括课程名称、授课老师、打分、
> 难度、掌握程度（以上均为正面）；课程给分标准、大致结构（以上为背面，均为可选项）。
> 卡片可手动添加与修改，双击卡片可修改。
> 卡片连接着一篇可编辑的笔记，卡片下方设计有记笔记按钮，点击即可跳转至笔记编辑页面。
> 如果前面的课程表是以表格方式填写则课程名称和授课老师直接从表格中自动拷贝填写。
> **课程卡片创建时自动同步创建笔记。**

### 单击翻转与双击修改怎么共存

两个手势落在同一个元素上，直接实现会打架。做法是**点击后等 200ms 再翻转**，
如果这期间来了第二下就不翻、直接进编辑。

反过来「先翻过去、双击时再翻回来」也能实现，但会有一次明显的「翻两下」抖动。
200ms 是权衡出来的：再短会漏判双击，再长翻转就显得迟钝。

翻转用 `rotateY` + `backface-visibility: hidden`，两个面都真实存在于 DOM 里
（而不是切换内容）——这样背面内容可以被选中复制，滚动也各自独立。

### 卡片不复制课表的课程信息

卡片只存「这门课我自己的记录」，课程名和老师是**新建时从课表带过来的一个副本**，
之后两边各走各的。这里没有做「课表改了自动同步卡片」：

同一门课在课表里出现三个时间段（周一三五），此时「以哪一格为准」根本没有正确答案。
强行同步只会让用户在某次改名之后发现卡片集体变了样，还找不到原因。

带过来的方式是一个下拉选择器，选项来自课表的 `cells` 按「课程名 + 老师」去重。
课表还没填也能手动输入——不能让「没填课表」变成「建不了卡片」。

### 跨存储的引用完整性放在 IPC 层

「建卡片 → 建笔记」需要同时操作两个存储，所以这段编排写在 `ipc/cards.ts`：

- 新建卡片 → 建一篇 `课程名_老师.md` 并回填 `noteId`；
- 卡片改了课程名 / 老师 → **只在这个笔记标题还是自动生成的那个时**才跟着改名。
  用户自己给笔记改过名（比如加了章节后缀），那是他的命名，不该被覆盖；
- 删卡片 → **不动笔记**。笔记是用户自己写的东西，删卡片顺手删笔记，
  是那种让人再也不想用第二次的体验；
- 删笔记 → 把指向它的卡片解除关联，而不是留一个断掉的 `noteId`
  （否则用户点「记笔记」会跳到一个空页面，还看不出为什么）。

放进任何一侧的 store 都会让它持有另一个 store 的引用，耦合方向会变得很难看。
IPC 层本来就能同时看到两边，放在这里最自然。

### 卡片编辑器的现状

卡片与笔记之间的**存储与联动**是这一节的重点：建卡片自动建笔记、
改课程名跟着改笔记名、删卡片不动笔记、删笔记解除关联。
编辑器本身见下一节。

自动保存是「输入停止后 800ms 写一次」+「切走页面或关闭时补写一次」，
既不会每敲一个字就落一次盘，也不会因为忘了按保存而丢东西。
字数统计单独再防抖一次（1200ms）——富文本模式下算字数要跑一遍
HTML→Markdown 转换，每次敲键都算的话长笔记会上手就卡。

## 十四、双模式笔记编辑器

### 需求

> 笔记编辑器采用 md 或者 word 格式编辑（用户可自行选择两者其一），
> 这个编辑器要有主流 md 格式编辑器和 word 的所有主要功能（记笔记用得到的）

### 一份源文件，两种编辑方式

```
        ┌──────────────┐
        │  x.md 源文件  │   ← 磁盘上只有这一份
        └──┬────────┬──┘
   getMarkdown │        │ getMarkdown
   ┌───────────▼──┐  ┌──▼──────────────┐
   │ CodeMirror 6 │  │ TipTap(ProseMirror) │
   │  Markdown 模式 │  │    富文本模式      │
   └───────────────┘  └───────────────────┘
              markdown-it ↕ turndown
```

两个编辑器**对外都只吐 Markdown**（`EditorHandle.getMarkdown()`）。
富文本内部当然是 HTML，但这个约定让「磁盘上只有一份 .md」在类型层面就成立，
调用方根本不需要知道当前用的是哪个编辑器。

### 统一的是命令，不是实现

「加粗」在两边的实现毫无共同点：Markdown 是往选区两侧插 `**`，
富文本是 toggleBold mark。但对用户来说它是同一个动作。

所以 `lib/editor/commands.ts` 定义的是一份**动作词汇表**，
两个编辑器各自实现，工具栏只认词汇表——「加粗」这个按钮一行都不用改就能两边通用。

Markdown 表达不了的命令（下划线、高亮、对齐）在 md 模式下**灰掉而不是藏起来**：
按钮位置不变，工具栏不会跳；灰掉则明确传达「这个模式不支持」。

### 换行语义跟着 Obsidian 走

`markdown-it` 配的是 `breaks: true`——单个换行也算换行。
标准 Markdown 会把单换行合并成一行，但笔记场景下用户就是习惯一行一件事，
而且 **Obsidian 默认也是这个行为**。既然笔记库要能直接当 Obsidian 库用，
行为就得跟它对齐。

### 表格往返：为什么最后没用 turndown-plugin-gfm

富文本里插的表格要存回 .md，得变成 GFM 语法。`turndown-plugin-gfm` 是现成的选择，
但它的表头判定是：

```js
parentNode.firstChild === tr && … && 每个单元格都是 <th>
```

而 **TipTap 生成的表格结构里，`<tbody>` 前面有一个 `<colgroup>`**
（用来固定列宽）。于是 `firstChild` 不是那个 `tr`，判定失败，
整张表格被当作「复杂表格」**原样保留成 HTML**——存进 .md 里就是一堆标签。

所以表格规则是自己写的，判定简单得多：**第一行的格子全是 `<th>` 就算表头**。
顺带去掉了这个依赖。

同类还有两处土办法，都是为了让「切一次模式」不产生无意义的文件改动：

- 列表项缩进：turndown 默认写 `-   文字`（三个空格，为了和 `1.  ` 对齐），
  而用户原本写的是 `- 文字`，来回切一次 git diff 就全是这种改动；
- 时间戳：写 frontmatter 时强制加引号，否则严格 YAML 解析器会读成日期对象。

### 安全：靠 CSP，不靠过滤 HTML

`markdown-it` 开了 `html: true`（否则用户笔记里的 HTML 会被转义，往返就废了）。
安全性由渲染层的 CSP 兜底：`script-src 'self'` 不含 `unsafe-inline`，
内联脚本与内联事件处理器根本不会执行；`img-src` 不放行外域，
所以 `<img src="http://…">` 连请求都发不出去。

**用黑名单去洗 HTML 是洗不干净的，分层防御才靠谱。**

### 两个编辑器都按需加载

CodeMirror 与 TipTap 加起来 2MB 出头。静态引入的话，它们会被塞进
**启动就要解析的主 bundle**——而「打开应用先看课表」这条路径上根本用不到它们。

所以两个编辑器都是动态 `import()`，各自成为独立 chunk：

```
index.js              112 kB   ← 启动时只加载这个
markdown-editor.js   1010 kB   ← 打开笔记页才加载
richtext-editor.js   1116 kB   ← 切到富文本才加载
```

只写 Markdown 的人永远不会下载 TipTap 那一份。

### 切到富文本前先备份

md 表达不了的能力（文字颜色、合并单元格）在互转时会退化。
与其事后说「抱歉丢了一点」，不如在切换前把原文件复制一份到
`.study-board/backups/`——**备份失败就取消切换**，宁可让用户重试一次，
也不要在没有退路的情况下转换格式。

## 十五、笔记库的文件监听与双向同步

### 需求

「笔记库要能直接当 Obsidian 库用」——这句话的前半段（能读、能写、
外部新增的能被认出来）在前几节已经做到了，但那都是**在用户点一下的时候
才去对账**。真正的双向同步还差一段：用户在 Obsidian 里写完切回来，
列表和编辑器得自己跟上，不用手动刷新。

### 谁来监听，为什么不在渲染层

监听放在**主进程**，理由和「为什么存储在主进程」是同一条：

- 渲染层的 CSP 是 `connect-src 'self'`，它连网络都发不出去，
  更不该去碰文件系统；
- 笔记库目录的路径只有主进程知道，渲染层拿到的永远是「相对路径 + 校验」；
- 只有主进程能同时看到笔记存储与卡片存储——而「外部把笔记删了，
  指着它的卡片必须解开关联」恰好需要同时看到两边。

监听的装配写在 `src/main/ipc/notes.ts` 里，和 `NOTES_DELETE` 处理器挨着，
因为它们是同一类事：**跨存储的引用完整性**。

### 关键决定一：对账返回差异，而不是让调用方去猜

`NotesStore.reconcile()` 原来只返回一个 `boolean`（变没变）。监听需要知道
**具体怎么变的**，于是它改成返回 `{ added, renamed, removed }`。

这里有一个必须由对账自己保证、不能推给调用方的不变式：

> 同一个 id 不会既出现在 `added` 里，又出现在 `removed` 里。

最容易出错的是**外部改名**。如果实现成「旧文件名不见了 → 删一条；
新文件名出现了 → 加一条」，那么在 Obsidian 里改个文件名，卡片与笔记的
关联就会无声地断掉。而我们的文件里本来就写着 id（frontmatter 里的 `id:`），
改名并不影响它——所以对账要把这个 id **认回来**，把它报成 `renamed`。

「认回来」之前还有一道判断不能省：**旧文件名必须先确认已经不在硬盘上了**。
用户把一篇笔记复制一份时，两份文件的 frontmatter 里是同一个 id，
不加这条判断，它们会每次对账都互相抢一次这个 id，翻来覆去没有尽头。

### 关键决定二：写入打标记——用指纹，不用时间窗

自动保存每 800ms 就要落一次盘。这些写入同样会产生文件系统事件，
不过滤的话，**用户每打一个字编辑器就会被重载一次**。

过滤的办法是「写入指纹」：每次写完立刻 `stat` 一次，把
`size + mtimeMs` 记在文件名的名下；收到事件时再 `stat` 比一次，
对得上就说明是自己刚写的。

为什么不用「刚刚多少毫秒内写的都忽略」这种时间窗：那是个猜出来的数，
短了会漏、长了会把用户紧接着做的外部修改也一起吃掉。
指纹是确定的——文件只要被人动过，size 或 mtime 必有一个变。

自检里有一条专门盯这件事：点一下工具栏的「分隔线」（会触发一次保存），
等两秒，然后看 `.cm-editor` 还是不是同一个 DOM 节点。是同一个，
就说明这次写入没有绕回来重载编辑器。探针同时把收到的事件原样带回来，
通过时那份列表应该是**空的**。

### 关键决定三：删除要两次确认才上报

有些编辑器保存文件是「先把原文件删掉，再写一个新的」。中间那一小段真空期
如果被当成删除，卡片关联就会被无谓地解开——等文件回来时 id 虽然认得出，
**关联却回不来了**。

所以第一次发现文件不见了，先记下来，过 800ms 再看一眼：
文件回来了就撤掉这次删除（那是保存的中间态），确实没了才上报。

这一步必须**直接看文件在不在**，不能再看一次对账结果——第一次对账
已经把那条索引删掉了，第二次对账根本不会再报它一遍，于是「等一会儿
再看一眼」会永远等不到确认，删除反而丢了。（这个坑在自检里当场踩到了。）

代价是真删除晚一秒才反映到界面上。对一个「跟随外部改动」的功能，
这完全无感；而查错一次的成本是用户丢一个关联。

### 关键决定四：对账在事件里重跑，不信事件类型

chokidar 报上来的 `event` 有 add / change / unlink 三种，但**我们不按它分流**。
理由是一次保存常常被拆成好几个事件，而「编辑器是先删再建、还是原地改写」
这种事没法从事件类型上分辨。

做法是把一批事件防抖合成一个集合，重新扫一遍目录比对——**是什么就是什么**。
这样一来，「先删再建」式的保存即使被拆成 `unlink` + `add`，重扫的结果
也是「文件还在，内容变了」，天然正确。

顺带两个细节：

- `awaitWriteFinish` 挡住「读到半截文件」：等文件大小稳定下来再报事件；
- 只认**笔记库根目录下的 `.md`**。`.study-board/` 里的索引、备份、回收站
  都是隐藏目录，必须排除——备份与回收站里的文件名长得像笔记，
  一旦被认进来，用户的列表里会冒出一堆 `2026-09-11T…__xxx.md`。

### 事件到了渲染层之后

主进程推的 `library-changed` 一定意味着**外部改动**（自己的写入在主进程
就被指纹滤掉了），所以渲染层只要处理三种情况：

| 情况 | 处理 |
| --- | --- |
| 换笔记库目录了（`reset`） | 把编辑器收起来，重新拉列表 |
| 变的不是正在编辑的那一篇 | 只刷列表 |
| 正在编辑的那篇被外部删了 | 从编辑器里收起来，并说明原因 |
| 正在编辑的那篇被外部改了 | 见下 |

「被外部删了」为什么必须把编辑器收起来：不收的话自动保存会在 800ms 后
把刚删掉的文件又写回来，用户会觉得「怎么删都删不掉」。

### 冲突：不替用户决定

正在编辑的这篇在外部被改动时，编辑器里可能有还没保存的内容。
这时**无论选哪边都是覆盖另一边**：

- 没改过（`dirty` 为假）→ 直接换成磁盘上的版本。这正是「双向同步」的意思；
- 改过 → 弹一次确认，两个选项都写清楚后果：
  「载入磁盘版本」会丢掉刚输入的内容；「保留我的内容」则稍后的自动保存
  会覆盖磁盘上这次的改动。

选「载入磁盘版本」时有一处必须小心：`open()` 开头会 `flush()` 一次，
所以**要先把 `dirty` 清掉**，否则它会把我们刚刚决定丢掉的那份内容又写回磁盘，
磁盘上的新版就这么被自己的旧版盖掉了。

### 自检怎么测这件事

`npm run smoke:sync` 让主进程直接往磁盘上写文件，模拟外部编辑器——
Obsidian 保存、VS Code 保存、记事本保存，落到文件系统层面都是同一件事。
来回七趟，每趟验一件事：

1. 打开笔记 + 自己写盘**不产生事件**（编辑器节点没换）
2. 外部新增 → 列表自己长出来，收到的事件恰好是 `add 外部新增的笔记.md`
3. 外部改动正在编辑的那篇 → 编辑器换成磁盘上的版本
4. 外部删除 → 列表收起，**并且卡片关联自动解开**（这条去磁盘上验）
5. 有未保存内容时撞上外部改动 → 先问一句；选「保留我的内容」编辑器不动
6. 同样的冲突选「载入磁盘版本」→ 编辑器换成磁盘上的内容
7. 外部改名 → 标题跟着换，**卡片仍然指着同一个 id**

第 1 条和第 7 条是重点：前者一旦失效，用户的打字体验会直接崩掉；
后者一旦失效，用户改个文件名就会悄悄丢掉卡片关联。
