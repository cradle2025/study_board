# 性能与内存

这份文档记录**怎么量**、**量到了什么**、以及**哪些优化做了、哪些没做、为什么**。

数字本身只对某一台机器有效，所以重点不是记住「2.75ms」，而是能随时把同一套测量重跑一遍。
后面任何人改了渲染路径或存储层，都应该能靠 `npm run bench` 判断自己有没有搞坏。

---

## 一、为什么单独做一套基准

常见的坑是拿微基准代替真实测量：`renderTable()` 单独跑当然快，但用户感受到的是
「双击格子 → 输入 → 保存 → 界面上看到新值」这一整条链路，中间夹着 IPC 往返和落盘。
分开量每个环节都很快，合起来才是真数字。

所以基准的做法是：**起一个真实窗口，用脚本驱动真实交互**，量端到端耗时。

还有一点和「只量 JS 堆」不同：图片解码后的位图不在 JS 堆里记账，
渲染进程的 JS 堆可能只有 10MB，而进程实际占用上百 MB。
所以内存一律取 `app.getAppMetrics()` 的**进程工作集**，那才是用户真正付出的物理内存。

## 二、怎么跑

```bash
npm run bench
```

它会：起窗口 → 造一份有代表性的课表（11 节 × 7 天，约一半格子填满，2 张课表照片）
→ 冷导航一次 → 连续保存 40 次单元格（前 6 次预热不计入）→ 热导航一次 → 输出报告并退出。

报告同时打到 stdout 和 `.preview/bench.json`（已 gitignore）。
测试全程跑在系统临时目录里，**不会碰到你真实的学习数据**。

### 报告里有什么

| 分组 | 说明 |
| --- | --- |
| `startup` | 启动拆解：Electron 自身启动 / 我们的初始化 / 模拟数据准备 / 窗口到首帧 |
| `mainPhases` | 主进程各阶段打点，时间基准是主进程 JS 起点 |
| `lazyLoads` | 懒加载依赖的加载耗时（目前只有 libheif） |
| `renderer.save` | 保存单元格的端到端耗时（p50 / p95 / 最慢） |
| `renderer.navToReadyMs` | 冷导航：点导航 → 数据取回并渲染完 |
| `renderer.warmNavMs` | 热导航：回首页再进来，同一指标 |
| `renderer.dom` | DOM 节点数与残留提示条数量 |
| `memory` | 每个进程的工作集，以及整应用合计 |

### 前后对比

```bash
# 改代码前跑 3 次
for i in 1 2 3; do npm run bench && mv .preview/bench.json .preview/before-$i.json; done
# 改完再跑 3 次
for i in 1 2 3; do npm run bench && mv .preview/bench.json .preview/after-$i.json; done

npm run bench:compare -- .preview .preview
```

`compare-bench.mjs` 取**中位数**而不是平均值——这类测量的尾部噪声很大（GC、系统调度），
平均值会被单次异常拖走。同时它会打出每项指标的 `最小~最大` 区间：
**两组区间不重叠，差异才算站得住**。

## 三、测量纪律（踩过的坑）

这一节比数字重要。

### 1. 必须等应用完全初始化完再开始计时

导航按钮在 `renderNav()` 阶段就存在了，而那时首页自己的课表还在加载。
第一版探针一看按钮出现就点，结果把「首页加载 + 课表页加载互相争抢」的结果
量成了课表首屏渲染耗时——**84ms**。修正后同一份代码量出来是 10ms 左右。

正确做法是等一个**语义上的完成信号**（这里是 `sb:shell-ready` 打点），
而不是等某个 DOM 元素出现。

### 2. 预热轮次不能计入统计

首次调用要付 JIT 编译、样式首次命中、渲染层刚起来的各种一次性成本。
不预热的话 p95 会被抬高一截，而且抬高多少完全取决于「什么时候开始测」，不可复现。
现在固定预热 6 次、统计后 40 次。

### 3. 等 DOM 更新要用 MutationObserver，不要轮询

轮询间隔会直接混进被测耗时里，让数值失真。MutationObserver 一有变化就被唤醒，
不会把「等」的时间算到被测目标头上。

### 4. 两组数据要交替采，不能「先量完旧的再量新的」

同一台机器在不同时段的负载差异，足够盖住你要验证的优化。
本次对比就是交替执行的（before → after → before → after…，各 6 次）。

## 四、本次优化前后的实测

环境：Windows 11 / Electron 44.3.0 / Chromium 152 / Node 24.20.0。
新旧代码交替各跑 6 次，下表是中位数。

| 指标 | 优化前 | 优化后 | 变化 | 区间是否重叠 |
| --- | --- | --- | --- | --- |
| 保存单元格 p50 | 4.20 ms | 2.75 ms | **−34.5%** | 不重叠 ✅ |
| 保存单元格 平均 | 4.24 ms | 2.79 ms | **−34.1%** | 不重叠 ✅ |
| 保存单元格 p95 | 5.35 ms | 4.00 ms | **−25.2%** | 不重叠 ✅ |
| 保存单元格 最慢 | 5.50 ms | 4.60 ms | −16.4% | 轻微重叠 |
| 压测后 DOM 节点数 | 485 | 442 | **−8.9%** | 不重叠 ✅ |
| 残留提示条 | 46 | 4 | **−91.3%** | 不重叠 ✅ |
| 渲染进程内存 | 148.2 MB | 109.5 MB | **−26.1%** | 不重叠 ✅ |
| 整应用内存 | 467.6 MB | 423.3 MB | **−9.5%** | 不重叠 ✅ |
| 主进程 RSS | 158.1 MB | 158.9 MB | +0.5% | 重叠，无变化 |
| 我方初始化耗时 | 6.62 ms | 6.55 ms | −1.0% | 重叠，无变化 |
| 窗口到首帧 | 127.0 ms | 134.3 ms | +5.7% | 重叠，无变化 |

**没变化的项也要如实写出来。** 上一版探针曾让「冷导航」看起来从 84ms 掉到 18ms，
那是测量缺陷造成的假象——修好探针后新旧代码都在 9~19ms 之间，没有差异。

启动方面：Electron 自己启动占 **133ms**，我们的初始化只占 **6.5ms**。
也就是说应用启动时间基本由 Chromium 决定，动我们那部分代码收益有限。

## 五、做了什么

### 1. 单元格保存改为单格增量重绘

保存一格的旧做法是：主进程返回整份课表 → 渲染层**重建整张表**（77~140 个节点）。
新做法由调用方带一个 `{ kind: 'cell', key }` 提示，面板只重画那一个 `<td>`。

这是本次最大的一笔：p50 掉了三分之一，渲染进程内存少了 26%。
结构变化（换模式、改节数、表头重命名）仍然走整表重建，那条路径本来就不频繁。

模板只有一份（`cellInnerHtml()`），整表渲染和单格重绘共用，
避免两条路径久了长得不一样——这类偏差很难靠测试发现。

### 2. 去掉重复的深拷贝

写方法（`setCell` / `setRows` / `removeImage`）原来各自返回一份 `structuredClone` 的快照，
而调用方（IPC 层）拿到后**丢掉不用**，转头又 `compose()` 深拷贝了一遍。
现在写方法返回 `void`，`get()` 是唯一的深拷贝出口，一次写操作只克隆一次。

### 3. 内容没变就不写盘

保存时先比对内容，完全一致就跳过落盘。

注意这里**没有**改成异步合并写。合并写能把文件写入移出关键路径，
但如果进程在这段时间内异常退出，用户最后一次编辑就没了。
实测一次落盘约 0.3~0.5ms，收益不值这个风险。

### 4. 提示条数量设上限

批量操作（导入多张图片、连续编辑）会在很短时间内产生一串提示条，
每条要等 2.6~5.2 秒才自己消失。压测里 40 次保存留下了 46 个提示条节点。
现在最多同时 4 条，超出就挤掉最旧的。

### 5. 浮层容器空了就摘掉

`position: fixed; inset: 0` 的全屏容器原来创建后就常驻，Chromium 会一直为它保留一层。
改成按需创建、空了自动回收，清理走微任务——这样「关掉悬停预览、紧接着打开编辑弹层」
这类一关一开的连招不会把容器拆了又建。

### 6. 清理工作移出启动关键路径

孤儿课表图片清扫（遍历目录）原本在 `initContext()` 里做，是启动路径上的纯清理工作。
现在挪到窗口 `ready-to-show` 之后——它不影响首屏能不能显示，就不该跟首屏抢时间。

### 7. 图片带上真实宽高

`<img>` 上补 `width` / `height` 属性，浏览器能在解码完成前就预留位置，
图片加载完不会让整块区域跳一下。
配套必须在 CSS 里写 `height: auto`——否则 HTML 的 `height` 属性会当成长度提示生效，
图片被拉成原始像素高。自检里加了渲染尺寸断言专门防这个回归。

### 8. 其他

- 悬停预览的位置改成**真要显示时才测量**。鼠标扫过一排空格子不再每次都触发强制布局，
  而且拿到的手永远是最新的（滚动中不会偏）。
- 表格单元格的 `transition` 只保留真正会变的 `background`，去掉从未变化的 `box-shadow`。
- `app-shell` 被卸载时退订设置变更事件，并清掉「当前路由」的记账。
  后者原来会导致元素重新挂载时 `go()` 认为「路由没变」直接返回，舞台永远空着。

## 六、试过但没做的

### `enableCompileCache()`（V8 编译缓存）

理论上能在第二次启动时省掉 JS 编译。实测不划算：

- 主进程产物只有 64 kB，且 V8 是惰性编译，`main:index-start` 打点在 **0.37ms**，
  说明我们自己的代码几乎不花编译时间；
- 启动的 133ms 是 Chromium 初始化，编译缓存对它没有任何影响；
- 唯一受益者是 libheif（2MB，懒加载，实测 **27ms**），而它只在**第一次导入 HEIF** 时加载，
  本来就在关键路径之外；
- 代价是要多一个缓存目录，便携模式下还和「数据全在程序目录」的承诺冲突，
  Node 在缓存不干净时还会往 stderr 打警告。

结论：不加。

### 异步合并写盘

见上文第 3 条，数据安全 > 0.5ms。

### 给表格容器加 `contain: layout paint`

理论收益很小（表格是容器的唯一内容），但有改坏布局的风险。
**没有测量支撑的 CSS 优化不加**——加了之后如果出现奇怪的样式问题，反而找不到原因。

### `ipc` 返回增量而不是整份课表

把 `setCell` 的返回值从整份 `TimetableData` 换成 `{ key, cell, filledCount }`，
可以省掉每次保存序列化整张表（约 8~20 kB）。

没做，是因为收益相比已经落地的单格重绘很小（序列化一次不到 0.5ms），
而代价是渲染层失去「一份完整、唯一可信的状态快照」。
真的需要时再改，`RenderHint` 这套机制已经为它留好了位置。
